## 2. Phase 0 —— `phase0-engineering-foundation`（P0，现在做）

把现有承诺做真实，为数据演进打地基。

**范围**：修 `club` 场景空计划；补完整 PWA 或把文案降级为移动 Web App；真实 JSON 下载/导入/校验/版本迁移；建立统一 Repository 接口；将反应/预判/张力结果纳入统一结果模型；建立训练执行事件与中途恢复；增加主流程 E2E 基线。

**验收标准**：
- 所有场景均能生成计划，或返回明确的不可生成原因；
- 导出文件可在空浏览器中完整恢复；
- 文档中的 PWA 能力有浏览器证据（或文案已降级）；
- 专项训练结果关页后仍可查看；
- 现有功能无数据丢失。

## 3. Phase 1 首个纵向切片 —— `phase1-single-leg-slice`（P0）

单腿稳定/下肢控制 → 步法稳定，打通评估到复测的完整闭环。

**链路**：每日疼痛/疲劳 Check-in → 单腿站 + 单腿坐站评估 → 左右差异与置信度 → 识别「下肢稳定候选 limiter」→ 生成单腿稳定/分腿蹲/启动制动计划 → 周末两点移动验证 → 4–6 周复测。

**验收标准**：
- 用户能看到为什么被判断为 limiter；
- Yellow 状态时高冲击动作被自动降级；
- 每个动作有退阶、进阶、停止条件；
- 复测使用相同协议；
- 改善后 limiter 可被撤销或降级。

## 4. Phase 2 —— `phase2-capacity-center`（P2）

Layer 0 基础能力中心：心肺、下肢、上肢、核心、活动度、平衡、睡眠/静息心率/体重腰围趋势，同时上线能力画像、limiter 引擎、训练配比与周期复测。

---

## 5. Phase 3 —— `phase3-specific-assessment`（P3）

反应跟随率与可测反应时分开；真实授权视频遮挡题库；视觉线索/旋转/落点/长短分维度统计；动态稳定、步法准确率与还原质量；连续球与疲劳后技术保持；ONE CUE 与量化球台验证关联；迁移分析。

---

## 6. Phase 4 —— `phase4-device-video`（P4）

CSV/平台导出适配；原生 Health Connect/HealthKit；可选云同步；训练视频关联；姿态估计与动作事件提取；大模型基于结构化证据生成解释（不越过规则引擎）。

## 8. 明确不做（每个子 change 的边界锚点）

1. 不用大模型替代医学判断，不做疾病诊断与医学风险评分；
2. 不用一个总分掩盖能力结构；
3. 不在闭环验证前堆满所有健康指标；
4. 不先拆微服务；
5. 不把编译通过 + 15 个单测通过当作产品正确；
6. 第一阶段不接 HealthKit/Health Connect；
7. 不直接上云端多用户；
8. 评估协议尚未稳定前不做大模型自动处方；
9. 不先建设复杂摄像头动作识别。

## 9. 五个问题闭环（最终验收锚点）

TT-Companion 最终应稳定回答以下五个问题，任何子 change 完成后都不得破坏既有可追溯性：

1. **今天是否适合训练？**（安全门 / readiness）
2. **当前真正限制我乒乓球表现的能力是什么？**（limiter 引擎）
3. **今天为什么练这些，而不是别的？**（处方引擎 + 解释）
4. **训练过程中发生了什么，质量如何？**（统一执行事件 + 质量反馈）
5. **几周后用什么证据判断它真的有效？**（周末验证 + 周期复测 + 迁移分析）

这五个问题能形成可追溯闭环，产品才算从「训练内容应用」升级为「个人乒乓球训练伴侣」。
